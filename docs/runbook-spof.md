# SPOF 런북 — 데이터 플레인은 한 대다

v1 데이터 플레인은 **단일 장애점**이다. 자동 페일오버는 없다. 콜드 스탠바이가
있고, 트래픽을 옮기는 것은 DNS 또는 상위 L4 다. 멀티 노드 HA 가 아니다.

숫자는 **v1 운영 정책**이다. [`docs/adr-spof.md`](./adr-spof.md) 가 확정한다.
랩에서 잰 SLA 가 아니다. 페일오버는 수동이다.

## 운영 정책

| 항목 | 정책 | 비고 |
|---|---|---|
| RTO (DP 호스트 손실 → 서비스 복구) | ≤ 15분 | 수동 페일오버 |
| RPO (설정 손실) | 0 | 정본은 PostgreSQL. 아티팩트는 재생성 |
| PG 손실 시 RPO | ≤ 5분 | PITR/스트리밍이 있을 때 |

## 백업 세 종

1. `bary backup` — spec-only 매니페스트 + head 리비전. 시크릿 바이트 없음.
2. PostgreSQL 덤프 — 정본.
3. SecretStore — 인증서 자료. **어디를 받는지는 드라이버가 정한다** (§4.8.1):

   | `BARY_SECRET_BACKEND` | 무엇을 받나 |
   |---|---|
   | `fs` (기본) | SecretStore 디렉터리 (`BARY_SECRETS`) |
   | `pg` | 2번 덤프에 이미 들어 있다 — **대신 KEK 를 따로 보관한다** |

⚠️ **`pg` 드라이버에서 KEK 를 잃으면 인증서 자료를 영영 못 연다.** 덤프에 있는 것은
암호문뿐이고, 그것이 이 드라이버의 요점이다(덤프 하나로는 키가 안 나온다). `BARY_SECRET_KEK`
는 **덤프와 다른 곳에** 두고 그 자체의 백업을 따로 가진다 — 같은 금고에 넣으면 봉투
암호화가 하는 일이 없다.

`BARY_SECRET_KEK_CMD` 를 쓰면 지킬 것이 바뀐다 (§4.8.2) — env 에는 명령만 있으므로
**그 명령이 닿는 것**(KMS 키 · 그 키에 대한 권한 · 암호문 파일)이 백업 대상이다.
셋 중 하나를 잃으면 결과는 KEK 를 잃은 것과 같다.

KEK 를 잃었을 때 남는 길은 재발급이다: 자료가 없는 인증서는 `501`/`nginx -t` 로 드러나고,
ACME 인증서는 새 주문으로, 업로드 인증서는 다시 올려서 복구한다. **설정은 안 잃는다** —
정본은 PG 이고 `material_ref` 는 참조일 뿐이다.

복구 리허설: 백업을 받아 `bary restore` 로 head 를 되돌린 뒤 `bary apply --plan` 으로
트래픽에 건다. restore 는 apply 가 아니다.

## 수동 페일오버

1. 스탠바이가 **동시에 listen 하지 않게** 한다. 포트 탈취를 막는다.
2. 같은 세대 아티팩트가 스탠바이에 있는지 본다.
3. DNS 또는 상위 L4 를 스탠바이로 돌린다. **자동이 아니다.**
4. 옛 호스트는 내린다.

리더 선출은 PG advisory lock 이다. 스탠바이 컨트롤 플레인은 읽기만 답하고
쓰기는 503 `not_leader` 다.
