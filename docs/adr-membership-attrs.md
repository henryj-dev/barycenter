# ADR — peer 별 속성을 멤버십 평면에서 어떻게 표현하는가 (2026-08-29)

§4.3.1 과 §4.4 가 표로 적어 두고 코드에 없는 필드들을 들이기로 했다. 그런데 그중 셋은
**필드 추가가 아니라 밸런서 작업**이다. 이 문서가 그것을 가른다.

- **상태** — **확정** (2026-08-29, 사람). §5·§6 이 `DESIGN.md` §4.4 의 표를 고쳤다
- **범위** — `Backend.maxConns` · `Backend.isBackup` · `Backend.adminState` ·
  `drain.deadline_s`
- **범위 밖** — 프로브 필드(§4.3.1)는 `HealthProber` 만 건드려 렌더·밸런서와 무관하다.
  따로 간다

---

## 1. 무엇이 문제인가

`max_conns` 와 `is_backup` 은 nginx 에서 **`server` 줄에 붙는 값**이다:

```nginx
upstream pool_app {
    server 10.0.0.1:80 max_conns=100;
    server 10.0.0.2:80 backup;
}
```

**멤버십 평면이 켜지면 그 줄이 없다.** upstream 에는 자리표시 하나만 남고 peer 는
`lua_shared_dict` 에 산다 — 그래야 백엔드가 바뀌어도 reload 가 안 걸린다(S1). v0.3 의
완료 판정이 그 사실을 못 박았다: *"멤버십 평면이 켜지면 백엔드가 conf 에 없으므로,
백엔드만 바뀐 변경은 산출물이 바이트 단위로 같다."*

그래서 이 둘은 **렌더할 자리가 없다.** 넣으려면 Lua 밸런서가 그 의미를 직접 구현해야
한다. STATUS 가 `passive` 를 뺀 이유가 정확히 같은 것이었다:

> `passive` 는 — 이 평면의 upstream 은 `server` 가 자리표시 하나뿐이라 peer 별로 셀
> 대상이 없고, Lua 로 다시 만들면 **멤버십의 주인이 둘이 된다.**

## 2. 이미 내려진 결정 하나 — 그리고 그것이 여기 안 통하는 이유

가중치는 같은 문제를 만났고 **반복**으로 풀렸다. `membership.ts` 가 그 근거를 적어 뒀다:

> 슬롯에 가중치를 실으면(`host:port|w`) admin 와이어가 넓어지고, 더 나쁘게는 **peer
> 문자열이 `in:<peer>` 카운터와 `/membership/inflight` 의 질의 키와 갈린다** — 접미사를
> 벗기는 자리가 넷이 된다. 반복은 와이어를 안 건드린다.

**이 근거는 지금도 유효하다.** peer 문자열은 네 자리에서 키다:

| 자리 | 쓰임 |
|---|---|
| 슬롯 목록 | 밸런서가 고르는 대상 |
| `in:<peer>` | 워커 간 공유 인플라이트 카운터 |
| `/membership/inflight` | http admin 질의 키 |
| stream admin `inflight` | stream 쪽 같은 것 |

**그런데 반복은 `max_conns`·`is_backup` 에 안 통한다.** 가중치는 *"몇 번 고를 것인가"*
라서 칸 수로 표현되지만, 상한과 backup 여부는 **횟수로 표현되는 값이 아니다.**

## 3. 무엇을 고를 수 있나

### ① peer 문자열을 넓힌다 — `10.0.0.1:80|max=100,backup`

**안 고른다.** §2 가 이미 판정한 것이고, 그때보다 나빠졌다 — 접미사를 벗기는 자리가
넷인데 지금은 그 넷이 서로 다른 두 평면(http admin · stream admin)에 걸쳐 있다.
하나만 안 벗기면 **그 peer 의 카운터가 영영 안 맞고, 밖에서 안 보인다.**

### ② 속성을 별도 dict 키로 나란히 민다 — **고른다**

슬롯은 지금 모양 그대로 두고, 속성 맵을 따로 민다:

```
slots:<upstream>   ["10.0.0.1:80", "10.0.0.1:80", "10.0.0.2:80"]   ← 그대로
attrs:<upstream>   {"10.0.0.1:80": {"max": 100}, "10.0.0.2:80": {"backup": true}}
```

- peer 문자열이 **키로 그대로 남는다** — §2 의 근거를 안 깬다
- `Slots` 타입이 안 바뀐다 → 옛 세대·옛 에이전트와 섞여도 슬롯 해석이 동일하다.
  속성을 모르는 쪽은 **속성 없이** 고르고, 그건 지금 거동이다
- 속성이 없는 배포(전부 기본값)는 이 키를 아예 안 민다 — **안 쓰는 배포의 거동이 안
  바뀐다**(가중치가 전부 1 일 때와 같은 성질)

대가: dict 키가 하나 늘고, 밸런서가 요청당 조회를 하나 더 한다. 상한(§7.3.1 의
`SLOT_EXPANSION_CAP` 과 같은 부류)이 필요하다.

### ③ 슬롯을 두 벌로 — 1차 / backup

`is_backup` 에만 쓰면 ②보다 단순하다. 하지만 `max_conns` 는 여전히 ②가 필요하고,
그러면 **두 방식이 공존한다** — 이 저장소가 반복해 경계하는 "자리가 둘" 이다.
②로 통일한다.

## 4. `max_conns` — 이름을 그대로 쓰면 거짓말이다

밸런서는 이미 `in:<peer>` 를 읽는다. `least_conn` 이 그 값으로 최소를 고르고(S6),
`in:` 은 dict 에 살아 **워커 간 공유**다. 그래서 상한을 거는 것 자체는 새 관측이
필요 없다 — 고를 때 `in:` 이 상한 이상인 peer 를 건너뛰면 된다.

**그런데 nginx 의 `max_conns` 와 뜻이 다르다.**

| | nginx `max_conns` | 여기서 할 수 있는 것 |
|---|---|---|
| 초과했을 때 | 큐에 넣거나 502 | **다른 peer 로 보낸다** |
| 전부 초과했을 때 | 큐 / 502 | ??? |
| 정확도 | 워커별 카운터 | dict 공유. 다만 **읽고 고르는 사이에 창**이 있다 |

셋째 줄이 결정을 요구한다. 전부 상한에 걸렸을 때:

- **거절한다** → 상한이 진짜 상한이 된다. 대신 백엔드가 멀쩡한데 502 를 낸다
- **최소인 peer 로 보낸다** → 상한이 **힌트**가 된다. 트래픽은 안 끊긴다

**후자를 고른다.** 이 제품의 상한은 백엔드를 보호하는 장치이지 SLA 가 아니고, 앞의
것을 고르면 *"백엔드는 살아 있는데 프록시가 끊었다"* 가 된다 — S8 이후 이 저장소가
반복해서 피해 온 모양이다.

**그래서 이름을 `maxConns` 로 쓰지 않는다.** 같은 이름이 다른 뜻이면 운영자가 nginx
문서를 읽고 우리 거동을 예측하게 되고, 그 예측이 틀린다. `softMaxConns` 처럼 **근사임이
이름에 드러나는** 것을 쓴다. 최종 이름은 이 ADR 을 받는 사람이 정한다.

## 5. `admin_state` — 넣지 않는다

§4.4 는 `admin_state ∈ {enabled, draining, disabled}` 를 **BackendSpec**(사용자 소유,
버전 관리)에 뒀다. 그런데 드레인은 이미 **운영 동작**으로 산다: `bary backend drain` 이
`backend_drain` 표에 쓰고 멤버십이 즉시 뺀다. 리비전을 안 지난다.

**둘을 합치면 드레인이 설정 변경이 된다** — changeset → plan → commit → apply 를 지나야
백엔드 하나를 빼게 된다. 그건 지금보다 **느리고 무겁고**, 무엇보다 §4.4 가 Spec 과
Status 를 가른 이유와 어긋난다. 드레인은 관측이 따라붙는 상태 전이이지 사용자가
버전 관리하는 의도가 아니다.

**합치지 않고 안 넣는다** — 2026-08-29 에 그렇게 정해졌고 §4.4 표에 반영했다. 세 값 중:

| 값 | 판정 |
|---|---|
| `enabled` | 기본값이다 — 필드 없이도 표현된다 |
| `draining` | **이미 있다.** `backend_drain` 표 + 멤버십 제외 |
| `disabled` | 이것만 스펙에 없다. 필요하면 `enabled: boolean` 으로 **따로** 낸다 |

`disabled` 를 지금 넣을지는 별도 판단이다 — 드레인과 달리 *"영구히 빼 둔다"* 는 뜻이고,
그건 백엔드를 지우는 것과 무엇이 다른지부터 답해야 한다.

## 6. `drain.deadline_s` — 스펙이 아니라 드레인 동작에 붙인다

§4.4 는 이것도 BackendSpec 에 뒀는데, §5 와 같은 이유로 자리가 틀렸다. 기한은
**그 드레인의 성질**이지 백엔드의 성질이 아니다 — 같은 백엔드를 두 번 드레인하면서
다른 기한을 줄 수 있어야 한다.

**드레인 동작에 붙이기로 정해졌다** (2026-08-29). `bary backend drain --deadline-s <n>` 이 `backend_drain` 에 함께 쓴다.
`drain_condition` 의 `deadline_exceeded` 는 그 값과 `drain_started_at` 으로 판정된다.
**이 둘은 이미 같은 표에 있다.**

## 7. 그래서 무엇을 하나

| | 무엇 | 어디를 건드리나 |
|---|---|---|
| 1 | 프로브 필드 (§4.3.1) | `HealthProber` · 모델 · DDL. **렌더 무관** |
| 2 | `drain.deadline_s` → 드레인 동작으로 | `backend_drain` · CLI · 드레인 판정 |
| 3 | 속성 채널 (②) + `softMaxConns` + `isBackup` | 모델 · 멤버십 · **Lua 밸런서** |

1·2 는 서로 독립이고 3 과도 독립이다. 3 이 제일 크고, 그 안에서도 **속성 채널이 먼저**
서야 나머지 둘이 올라탄다.

`Model` 이 넓어지므로 **표면 A 가 움직이고 동결 카운터는 0 으로 간다.** 그것은 이미
받아들인 대가다 — 2026-08-29 의 결정이 *"필드를 먼저 들이고 그 뒤에 다시 쌓는다"* 였다.

## 8. 이 ADR 이 답하지 않는 것

- **`softMaxConns` 의 최종 이름.** 근사임이 드러나야 한다는 것까지가 여기의 판정이다
- **`disabled` 를 넣을지** (§5) — 백엔드 삭제와 무엇이 다른지 먼저 답해야 한다
- **속성 맵의 상한** — `SLOT_EXPANSION_CAP` 처럼 실측으로 정한다
- **`is_backup` 과 해시 알고리즘의 충돌** — §4.3.1 이 이미 금지로 적었다. 검증기가 지되,
  그 제약이 실제로 필요한지는 밸런서를 짜면서 확인한다
