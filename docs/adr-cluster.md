# ADR-CLUSTER — 한 클러스터의 모든 호스트가 같은 세대를 서빙한다

날짜: 2026-10-29
상태: 채택 — 구현 #118
바꾸는 결정: ADR-SPOF 의 「멀티 노드 HA 는 범위 밖」 중 **데이터 플레인** 부분

## 결론

클러스터는 **설정 PG 하나를 함께 쓰는 barycenterd N 대**다. 쓰기와 커밋은 리더 하나가 한다.
**적용은 모든 호스트가 각자 한다** — 리더가 활성화한 세대를 다른 호스트(팔로워)가 PG 에서 읽어
자기 nginx 에 같은 세대를 활성화한다. 트래픽은 DNS 다중 A 레코드가 나눈다.

## 배경

운영 배치: 각 클러스터(`util-icn-vtr` 등) 안에 `web-01`, `web-02` … 가 늘어난다.
`util-icn-vtr.barycenter` 는 web-NN 의 공인 IP 를 담은 **다중 A 레코드**이고, 서비스는 그 이름을
CNAME 으로 가리킨다. 그러니 같은 클러스터의 모든 web-NN 은 **같은 설정으로 같은 트래픽**을 받아야 한다.

지금 구조는 이것을 못 한다 (코드로 확인했다):

- 리더 아닌 인스턴스는 **콜드 스탠바이**다. 자기 nginx 를 활성 세대로 올리는 경로가 없다.
- 헬스 프로브와 멤버십 반영이 리더에서만 돈다. 리더 아닌 nginx 는 헬스 변화를 못 받는다.
- 인증서 자료 기본 저장소(`fs`)는 호스트마다 따로다.

## 결정

| 항목 | 결정 |
|---|---|
| 켜기 | `BARY_CLUSTER=1`. 끄면 지금 동작 그대로다(리더 아닌 인스턴스는 콜드 스탠바이) |
| 노드 이름 | `BARY_NODE_NAME`(기본 `hostname:port`). 클러스터 안에서 겹치면 안 된다 |
| 쓰기·커밋·plan | 리더 하나. 지금처럼 PG advisory lock 과 펜싱 토큰이 정한다 |
| 리더의 적용 | 지금과 같다. 리더가 자기 nginx 에 활성화하고 `operations` 에 기록한다 |
| **팔로워의 적용** | 주기마다(기본 3초) PG 의 **활성 오퍼레이션**(가장 큰 epoch 의 `activated`)을 읽는다. 자기 nginx 의 epoch 와 다르면 그 리비전을 다시 렌더해 **같은 이름의 세대**(`r<rev>-e<epoch>`)를 만들고 자기 DP 에이전트로 활성화한다. `operations` 에는 쓰지 않는다 |
| 팔로워의 펜싱 토큰 | `leader_token_seq` 의 마지막 값을 쓴다. 팔로워는 리더가 아니다 — PG 가 「활성」이라고 한 것만 옮기므로, 토큰은 「지금까지 발급된 어느 리더보다 낮지 않다」만 증명하면 된다 |
| 멤버십·헬스 | 프로브는 리더만 한다(한 위치에서 본 헬스). 팔로워는 주기마다 PG 의 헬스로 자기 nginx 의 멤버십을 갱신한다(`projectHealth` — reload 없음) |
| 노드 상태 | 새 테이블 `cluster_nodes`. 노드마다 마지막 신호, 역할, 활성 세대, 마지막 오류를 쓴다. API `GET /api/v1/cluster/nodes`, CLI `bary get cluster/nodes` |
| 부분 실패 | **노드마다 따로다.** 한 노드가 활성화에 실패하면 그 노드만 옛 세대로 남고 오류를 보고한다. 전체 롤백은 하지 않는다 — 실패한 노드는 DNS 에서 빼는 것이 운영 절차다 |
| 인증서 자료 | 클러스터 모드는 **`BARY_SECRET_BACKEND=pg` 를 요구한다.** 아니면 기동을 거부한다 |
| 리더 아닌 노드의 쓰기 | 지금처럼 `503 not_leader` + `holder`. GUI 는 리더 노드로 가는 링크를 보여 준다(`BARY_NODE_URL`). 리더로 대신 넘기는 것은 후속이다 |

## 하지 않는 것 (이 ADR 범위 밖)

- **ACME http-01 의 클러스터 전체 응답.** 챌린지 토큰은 리더 nginx 의 dict 에만 있다. CA 가
  다중 A 레코드로 다른 호스트에 오면 실패한다. 클러스터에서는 dns-01 이나 업로드 인증서(예:
  Cloudflare Origin CA)를 쓴다.
- 노드별 헬스 관점. 헬스는 리더 한 곳에서 본다.
- 리더로 쓰기 넘기기(프록시). 후속 이슈로 둔다.
- 자동 DNS 제외. 실패한 노드를 DNS 에서 빼는 것은 운영자 또는 상위 헬스체크의 일이다.

## 결과

- 호스트 하나가 죽어도 나머지가 트래픽을 받는다. 리더가 죽으면 다른 노드가 락을 잡고 리더가 된다
  (쓰기만 잠깐 멈춘다 — 데이터 플레인은 계속 서빙한다).
- 적용 결과가 「리더 활성화」와 「노드별 수렴」 둘로 나뉜다. 화면은 둘을 함께 보여 줘야 한다
  (예: `r12-e10 · 3대 중 3대`).
- ADR-SPOF 의 RTO(수동 15분)는 **쓰기 경로**에만 남는다.

## 운영 — 노드 붙이기

모든 노드가 **같은 설정 PG**(`--dsn`)와 **같은 KEK** 를 쓴다. `--with-postgres` 는 노드마다 PG 를 따로
세우므로 클러스터에 쓰지 않는다.

```sh
sudo deploy/install.sh --dsn postgres://bary:…@config-pg:5432/bary_util_icn_vtr \
  --env BARY_CLUSTER=1 \
  --env BARY_NODE_NAME=web-02 \
  --env BARY_NODE_URL=https://web-02.util-icn-vtr.public.tinyuniver.se:8443 \
  --env BARY_SECRET_BACKEND=pg --env BARY_SECRET_KEK_CMD='…'
```

- 먼저 뜬 노드가 리더다. 리더가 내려가면 다른 노드가 락을 넘겨받는다(쓰기만 잠깐 멈춘다).
- `bary get cluster/nodes` — 노드마다 역할·활성 세대·상태·마지막 오류.
- 팔로워 주기는 `BARY_CLUSTER_SYNC_MS`(기본 3000). 「연락 없음」은 그 5 배를 넘긴 신호다.
- 노드를 DNS 다중 A 레코드에 넣기 **전에** 그 노드가 `in_sync` 인지 본다.

## 검증

- `tests/store/cluster-follow.test.ts` — 실물 PG, 가짜 DP 두 개: 같은 이름의 세대, fence 후 활성화,
  토큰은 시퀀스·리더 토큰 중 큰 것, `operations` 무변경, in_sync, 실패 기록, stale.
- `tests/e2e/cluster.test.ts` — **실물 엔진 두 대 + PG 하나**: 리더 적용 → 팔로워 nginx 가 같은 트래픽,
  노드 목록, 팔로워 쓰기 503, 새 리비전 추종, **리더를 내리면 팔로워가 리더가 되어 적용한다.**
